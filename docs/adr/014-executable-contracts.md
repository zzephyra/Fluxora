# ADR-014: 补齐可执行契约与恢复边界

## Status

Accepted — 2026-09-27。依据本次用户“重新分析，并且彻底完善文档缺失部分”的明确授权完成文档修订。只授权本轮文档完善，不表示业务代码已实现。

## Context

原架构已确定组件和原则，但状态图漏掉提交拒绝/取消失败，幂等范围易被误解为只有三个字段，跨模块 Service 提交边界不明确。Outbox 的队列投递与消费完成、重建水位、撤权后的后台收尾缺少执行契约。API、权限、RAG 和前端需要统一默认值，避免实现者自行设计第二套规则。

## Decision

1. ARCHITECTURE.md 保持唯一总入口；docs/specs 保存主题细则，AGENTS 引导阅读，不恢复旧 architect.md。
2. 外层 Service 拥有 UoW，内部跨模块 Service 不提交；业务、幂等记录和 Outbox 原子提交。
3. 幂等唯一键包含 project_id、actor_id、operation、idempotency_key；明确请求哈希、重放、删除和保留窗口。
4. 保持既有公开状态词汇，补全允许转移；结果不明用 reconciliation_required，不允许盲目重发。此项细化 ADR-009。
5. event_deliveries 分消费者/索引目标记录完成，不能把 broker 确认当作完成。以注册目标、快照、版本投影及短 PG 写屏障解决重建增量与切换；细化 ADR-004。
6. 撤权阻止新生成，系统恢复身份可对已有任务查询、取消和清理；细化 ADR-007 的后台授权规则。
7. API 固定 OWNER/MEMBER 权限、上传两阶段、Cookie/CSRF、DTO 和 SSE snapshot；补充任务与消息的可恢复输出。
8. RAG 的授权编排保留在 Service，LangChain 不自行执行越权检索；固定召回/上下文默认策略和记忆修订语义。
9. 固定首期 UI 基线及运行默认值。仍需外部提供真实供应商、账号和生产环境，不虚构已完成状态。

## Alternatives

- 继续只写高层原则，让实现各自决定：会产生不兼容接口和恢复行为。
- 把所有细节重复放入总文档和每个 ADR：容易漂移，改用主题规范的单一引用。
- 增加新工作流框架或状态系统：首期无需新基础设施，用当前 PG/Worker 边界即可表达。

## Trade-offs

更多显式契约提高实现约束，但文档变更必须随 API 和测试一起维护。索引切换屏障引入短时写入等待，因此设定超时、中止及恢复路径，不在全量重建期间持锁。未决供应商提交可能需要人工核对，这是避免重复外部操作的必要边界，不承诺 exactly-once。

## Consequences

业务实施以 [规范索引](../specs/README.md) 为入口。真实 Port、迁移、测试和 CI 必须逐阶段对齐；已有骨架不自动满足新增契约。无新业务框架、数据库或计费系统。

## Migration

本轮仅文档变更，无数据库迁移。实施表结构时新增 Alembic 迁移；不得改写既有空基线冒充已部署业务迁移。已确认历史 ADR 保留，只对被本记录细化的规则更新链接与解释。
